# Plan — closing the gaps of TODO §17 (2026-10-09)

Scope: everything in TODO §17 that can be done, plus the open verification work of §15–16. The app is macOS only;
no Windows or Linux packaging work. Each item lists the data model, core, GUI, user guide and test work, with the
files that change today. Work goes in branches off `mac-ci`, one PR per phase, full suite green
(`QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q`) before merge. Every new project field must be optional in
`project.json` so older experiments still open, and the ANY-maze column names in `core/anymaze.py` are used where a
measure already exists in ANY-maze.

Status (2026-10-10): every phase is done — 1 (#4, #5), 2 (#3), 3 (#6), 4 (#8), 5 (#10), 6 (#9), 7 (#11) and the
definitions of phase 8 item 2 (#7). What could not be done (numerical agreement on a shared video, hardware, the
rat pose model, Good / Poor tracking quality, the Developer ID build) is listed in TODO §15–17.

Order: phases 1–2 change what labs can do at all; 3–5 are medium-impact analysis and workflow; 6 is hardware and
security; 7 is polish; 8 is verification that runs alongside everything else.

## Phase 1 — Camera-free "I/O only / Operant" mode (high)

Goal: a protocol mode in which tests run on the computer's clock with procedures, I/O devices, keys and result
variables, with no camera or video. Operant chambers, running wheels and home-cage I/O then work out of the box.

Core (`manymaze/core/live.py`):
1. Split the camera-independent half of `LiveSession.__init__` (engine construction, `LiveIOLog`, popups, recording
   log, variables, `_freeze_thr` excluded) into a mixin `_ProcedureHost` used by both `LiveSession` and a new
   `IOSession(_Scoring)`. The engine already runs on the clock when frames stop (`_run_without_frames`,
   live.py:1174): make that path the *only* loop of `IOSession`, ticking at `tick_hz` (default 50 Hz) from a
   `threading.Timer`-free loop in its own thread, with `update_state` fed `detected=False` and no positions.
2. `IOSession` keeps `start_mode` "manual" | "key" | "input" | "clock" (no "on_detection" / "experimenter_leaves";
   `check_before_test` rejects procedures that use zone / position events in this mode with a clear message).
3. End of test: duration, procedure `end_test`, key, input, or training criterion — same as `LiveSession`.
   `test.io_events`, `result_variables`, `pauses`, `events` saved as today; `test.video = ""`, `test.status =
   "io"`.
4. `core/livegroup.py`: `LiveEntry` without a `SourceRunner` (`source is None`); the group clock schedule, collective
   start / pause / stop and `ClockSchedule` work unchanged.
5. `core/measures.py:339 analyse`: accept `track=None` → skip kinematics; `_results` still produces key, I/O,
   result-variable and information columns. `core/export.py`, `core/plots.py`, results table: a test without a track
   shows "–" for tracking measures instead of raising.
6. `core/project.py`: `Project.mode` gains `"io"`; `Project.operant_preset` (None | "med_associates" | "coulbourn" |
   "lafayette" | "custom") that pre-fills `io_devices` with named inputs / outputs (levers, nose pokes, lights,
   feeder, shocker, house light) through the Arduino / Firmata / NI / LabJack drivers. Presets live in
   `core/ioconfig.py` as data.

GUI:
7. `gui/pages/experiment.py:33 MODES` += `("io", "I/O only — procedures and devices, no camera")`; Protocol explorer
   hides *Animal tracking* and *Apparatus* elements in this mode (apparatus optional: keep it if a user wants zones
   for a touch screen).
8. `gui/pages/live/`: new `io_panel.py` (test clock, I/O status lights, live input / output counts from
   `core/livemonitor.py`, result variables, procedure log, scoring keys from `live/keys.py`), used by `single.py` and
   `multi.py` grid cells when the entry has no source. *Add tests* in the Test schedule for this mode creates tests
   without videos.
9. Test schedule and Review pages: a test with no video opens the event / I/O log review (reuse the I/O results table
   of `testview/`), no video widget.

Docs / tests: USER_GUIDE §1 (modes) and §7 (running tests) get an *I/O only* subsection; tests
`tests/test_io_session.py` (clock-driven procedures with fake devices, start / pause / end, autosave, criterion end),
`tests/gui/test_io_mode.py` (mode switch hides tracking pages, live panel arms and finishes a 2 s test offscreen,
results show key and I/O columns). ~1 week.

## Phase 2 — Calculations: user-defined measures (high)

Goal: formulas over existing measures, per test and per period, usable everywhere a measure is.

Core:
1. New `core/calculations.py`: `Calculation` dataclass (`name`, `expression`, `unit`, `decimals`, `on_blank`:
   "blank" | "zero"); `evaluate(calcs, row: dict) -> dict` adds the computed columns to a results row. Expressions
   use the safe evaluator of `core/procedures/expr.py` (already sandboxed, has maths / random functions), with
   measure names quoted as `[Open arms: time (s)]` and resolved from the row; dependencies between calculations
   are ordered topologically, cycles rejected by `validate_calculations`.
2. `Project.calculations: list[dict]` saved in `project.json` (next to `training_criteria`, project.py:180).
3. Apply in one place: `core/measures.py:_results` end (so segmented periods, exports, HTML reports, XML and
   statistics all see them). Information columns are also readable in formulas (e.g. body weight for dose per kg).
4. `core/workflow.py:Criterion.measure` and `core/periods.py` anchors may name a calculation (phase 4 uses this).
5. `core/anymaze.py`: import ANY-maze's calculation names if present in the XML export (they appear as plain
   measure columns; map by name).

GUI:
6. Protocol explorer: new element *Calculations* (`gui/pages/experiment.py ELEMENTS`) with a table (name, expression,
   unit, decimals) and an expression editor that offers a searchable list of measure names (reuse the *Select data*
   tree from `gui/pages/results/dialogs.py`) and live validation; errors shown inline as in the procedure editor.
7. Results table: calculated columns grouped under *Calculations* in `results/table.py GENERAL_PREFIXES` logic;
   Statistics measure picker lists them.

Docs / tests: USER_GUIDE §9 *Calculations* with the EPM open-arm example; `tests/test_calculations.py` (evaluation,
blank handling, ordering, cycle error, per-period rows, export columns), `tests/gui/test_calculations_ui.py`. ~3 days.

## Phase 3 — Saved reports, statistics settings, event-ended periods, jump removal (medium)

Reports:
1. `Project.reports: list[dict]` — `{name, measures, info_columns, segmented, periods_mode, hidden}`;
   `Project.statistics: dict` — the Statistics page's last factors, test, post-hoc, alpha (phase 7 item 3).
2. `gui/pages/results/page.py:set_project` restores the project's default report instead of clearing; a *Report ▾*
   combo on the ribbon (New / Save / Save as / Delete / Set as default); `exports.py` and the HTML report use the
   current report. CLI `manymaze project DIR results --report NAME`.
3. `gui/pages/statistics.py` reads / writes `Project.statistics` on change.

Event-ended periods (`core/periods.py`):
4. Period dict gains `end: {"anchor": ..., "zone"/"behaviour"/"channel"/"calculation", "occurrence", "offset_s"}`;
   `duration_s` kept for the old form. `resolve_periods()` returns `(t0, t1)` with `t1` = first matching end event
   after `t0` (+ offset), else test end; a period whose end never happens is reported with a flag so the results
   show it ended at the test end (ANY-maze behaviour).
5. GUI period editor (`gui/pages/base.py` ANALYSIS_SPEC / `protocol_pages.py`): *Ends* group (fixed duration | at
   event) mirroring the *Starts* group.

Jump removal:
6. `AnalysisSettings.max_jump` (units / frame, 0 = off) and `max_jump_speed` (units/s) in `core/measures.py:46`;
   `core/track.py`: `Track.remove_jumps(max_speed)` marks a detection missing when its displacement from the last
   good position implies a speed above the limit *and* the next frame returns near the previous position (a true
   jump), so genuine fast runs are kept. Applied in `core/tracking.py:930` before `interpolate`, and in the Review
   page's *Apply detection settings*. Detection settings form gains the two fields with a *Jumps removed: N* counter
   in the track-quality info column.

Tests: `tests/test_reports.py`, extend `tests/test_periods*.py` / `tests/test_tracking_extras.py` (synthetic track
with 3 injected jumps → removed, a straight sprint → kept). ~4 days.

## Phase 4 — Stage end rules, FST / TST mode, units, Barnes UNMC (medium / low analysis)

Stage end rules (`core/workflow.py:Criterion`):
1. Add `min_trials: int = 0` (criterion cannot be met before this many trials) and `variability: {"measure",
   "trials": N, "stat": "sd" | "cv", "max": value}` — met when the SD / CV of the measure over the last N trials
   is ≤ max (ANY-maze 7.30's "acceptable variability"). Both evaluated in `check_criteria` with the existing
   consecutive rule (`all` must hold). `from_dict` keeps old criteria working.
2. GUI `gui/pages/protocol_pages.py` stages editor: *Minimum trials* spin box and a *Variability* row.

Forced swim / tail suspension mode:
3. `core/freezing.py`: `immobility_from_motion(motion, fps, s)` — the FST/TST definition: immobile when the motion
   index (pixel change, already computed) stays below `fst_threshold_pct` for ≥ `min_fst_immobile_s`, with
   "small movements to keep the head above water" allowed by a higher threshold than freezing and *no*
   translation requirement; climbing / swimming / immobile three-state split optional (`fst_three_state`).
4. `AnalysisSettings.immobility_mode: "speed" | "motion"`; templates `forced_swim` and `tail_suspension` set
   `"motion"` and the FST measure names (time immobile, latency to first immobility, immobility bouts, climbing /
   swimming time) in `core/template_measures.py:466` instead of renaming freezing. Protocol page shows the FST
   settings group when a template of that family is chosen.

Units:
5. `Apparatus.distance_unit: "mm" | "cm" | "m"` (default cm; stored, `px_per_cm` stays the internal scale);
   `Apparatus.scale` returns the chosen unit; the unit label used by measure names (`core/measures.py` builds names
   with `u`) and exports follows. Calibration dialog gains a unit combo; speeds use unit/s.

Barnes UNMC:
6. `core/template_measures.py:312 classify_barnes_strategy(..., method="classic" | "unmc")` with the UNMC rules
   (direct ≤ 3 holes away and no more than one error; serial = consecutive holes in one direction; mixed otherwise)
   plus ANY-maze 7.54's revision (an initial wrong direction then serial still counts as serial);
   `AnalysisSettings.barnes_strategy_method`.

Tests: `test_workflow.py` (min trials, variability met / not met), `test_measures_parity.py` (FST on a synthetic
bobbing animal: immobile despite head motion; a swimming animal: mobile), units in `test_core.py`, Barnes in
`test_analyses.py`. ~4 days.

## Phase 5 — Lens distortion, montage, lighting changes, animal presets (medium / low video)

1. `core/camera.py:TransformedSource` gains `undistort` (camera matrix + k1 k2 p1 p2 k3) applied with
   `cv2.initUndistortRectifyMap` once per frame size (maps cached). `camera_settings()` stores it per camera;
   `Test.undistort` stores it per video test (set in the Apparatus page *Video* group: *Lens correction…*).
   Calibration dialog in `gui/pages/live/calibration.py`: checkerboard capture (≥ 8 views, `cv2.calibrateCamera`)
   or a single *barrel strength* slider (k1 only) with a live preview; the apparatus is then drawn on the corrected
   frame, and tracking reads corrected frames so the existing geometry is untouched.
2. Montage > 2 sources: `merge_frames(frames: list, layout: "row" | "column" | "grid")` and `SourceSpec.merge` as a
   list; the camera options dialog lists up to 4 sources with a layout picker.
3. *Ignore lighting changes* (`DetectionSettings.lighting_compensation`): before background subtraction, scale the
   frame's grey level so its median over the arena mask matches the background's median (per arena, per frame,
   `core/tracking.py` detection path); documented limitation: local shadows are not removed.
4. Animal presets in the detection settings form (`gui/pages/base.py DETECTION_SPEC`): *Mouse / Rat / Hooded rat /
   White animal on sawdust / Zebrafish* that set contrast, body-size limits, erosion and `lighting_compensation`;
   hooded rat: track the union of dark and light parts by using the background difference magnitude (both signs)
   — `DetectionSettings.contrast = "both"` already exists for "auto"; verify with a synthetic two-tone animal.
5. Rat pose model: add DeepLabCut *SuperAnimal-TopViewRat* (if a released ONNX-convertible checkpoint exists; else
   note as not available) to `core/pose.py` MODELS with its licence; the pose dialog lets the user pick the species.

Tests: undistort round trip on a synthetic grid (straight lines after correction), 3-source montage shape,
lighting step change keeps the centre error < 4 px, presets change the expected fields. ~4 days.

## Phase 6 — Security, sync element, analysis plug-ins, sensors (medium hardware / facility)

Users and passwords:
1. `core/project.py`: `Project.users` entries become `{name, role: "admin" | "user", pw_hash (scrypt, salted) |
   None}`; `Project.security = {"reveal_codes": "admin" | "anyone", "lock_protocol": bool}`. Experiments without any
   password behave as today (no prompt). The first user who sets a password becomes admin.
2. `gui/main_window.py` *Current user*: asks for the password when the chosen user has one; `gui/pages/animals.py:160`
   reveal-codes and the protocol element pages check `security`. *File ▸ Protect experiment…* sets an optional
   experiment password: `project.json` is then stored encrypted (AES-GCM via `cryptography`, key from scrypt);
   `archive.py`, CLI and the lock file handle the encrypted form (CLI reads `MANYMAZE_PASSWORD`). This is
   convenience-grade security, documented as such (ANY-maze's own words are "casual security").

Synchronisation element:
3. `Project.sync = {"device", "channel", "test_start": bool, "test_end": bool, "per_frame": bool,
   "per_position": bool, "width_ms"}`; `LiveSession` toggles the output from the frame loop (`per_frame` on every
   captured frame, `per_position` on every stored position) through the device's fastest path (the Arduino firmware
   gains a `SYNC` command that pulses from the ISR for jitter-free timing; NI / LabJack use their digital line).
   Hardware element page: *Synchronisation* group. Tests with fake devices count pulses == frames.

Analysis plug-ins:
4. `core/procedures/plugins.py` → `core/plugins.py` with two kinds: procedure plug-ins (existing) and analysis
   plug-ins: `register_analysis(name, fn)` where `fn(test, project) -> {"series": {name: (t, values)}, "measures":
   {name: value}}`; series are stored in `test.extra_series` (`core/series.py` already holds time series) and
   exposed as analogue-signal-style measures per period and per zone through `core/iomeasures.py`; a CSV / TSV
   file importer plug-in ships (timestamped columns, aligned with a sync pulse or the test start) so heart rate,
   photometry or Spike2 exports work without code. Entry point group `manymaze.analysis_plugins`.

Sensors and small I/O items:
5. `core/ioconfig.py:37` sensor types += `sound` (dBA) and `ultrasound` (peak kHz / dB) with the generic sensor
   measures; `Project.require_weight_before_test` (block arming until the balance returned a weight today);
   `Project.start_switch_delay_s` applied in `LiveSession` start handling.

Tests: password round trip, encrypted project open / save / archive, admin-only reveal in the GUI, sync pulse count,
plug-in series → measures, CSV plug-in alignment. ~1 week.

1. **Numerical agreement with ANY-maze** (§15): find or produce one video with ANY-maze's own results. Options:
   ask a lab with an ANY-maze licence to run the demo open-field video and share the XML + results; or use a
   published dataset that includes ANY-maze outputs *with a licence* (the CowenLab water-maze export already used
   has none, so it stays opt-in). Extend `scripts/verify_anymaze.py` to compare distance, speed, immobility,
   freezing, rotations and zone measures with tolerances, and keep it as the opt-in `MANYMAZE_ANYMAZE_XML` test.
2. **Definitions left open in §16**: implement "behaviours count as activity" (a per-key flag; Activity = mobile or
   doing such a behaviour, which also closes the ambiguity with FST); partial rotations (2.34–2.36) as quarter / half
   turn counts; investigation-based zone I/O and key measures; per-zone encoder / analogue / pump measures;
   event measures (21.x). Each with a `test_anymaze_definitions.py` case citing the section.
3. **Hardware**: a check-list issue per device family (Arduino firmware 1.2 compiled and run on an Uno / Mega with a
   logic analyser for pulse timing; Firmata; one serial balance; one New Era pump; a UVC capture card; a Basler
   camera via pypylon) — recorded in TODO §7 as done only after a real run. Firmware: add a CI job that compiles
   `manymaze_io.ino` with `arduino-cli` for AVR and SAMD so it never regresses again.
4. **Release**: tag `v0.2.0` once phases 1–3 land, run the signed / notarised build with a real Developer ID (the
   script is ready; it needs the secrets), publish the DMG as a GitHub release so *Help ▸ Check for updates* has a
